# HarnessIR 参考 Retouch：最初目标与后续修改依据

日期：2026-10-25。本文复原用户已经表达的目标与已同意的范围，作为后续方案、实验和工程修改的共同依据；不是新增实验结果，也不表示已经完成远端工程修改。

## 1. 最初要实现的系统

将 HarnessIR 的诊断、按需证据、提示编译、图像执行、验证反馈闭环，完善为能够接收源图 A 和参考图 B 的参考引导 Retouch 系统：理解两图的摄影外观及其差异，在保持 A 的内容、身份、文字、构图、几何与可信细节的前提下，将有证据支持、符合用户要求的参考外观迁移到 A，得到 C，并独立核验任务是否完成。

参考输入必须影响整个系统的决策。诊断产生的差异及证据要决定修改目标，目标要实际进入编辑条件，验证要检查同一批目标，反馈要针对具体残差。

原始仓库的具体业务对象是 Modular Neural ISP prediction A，以及同场景、非像素对齐的 iPhone 17 reference B。开发案例用于验证流程；未核实的 A 来源不能自动标注为 Modular Neural ISP prediction。实际输入来源在本地记录，个人照片及采集元数据不随代码发布。

## 2. 已明确的输入输出角色

| 对象 | 职责 |
|---|---|
| A：源图 | 唯一的内容事实来源，包括人物身份、表情、物体、可读文字、视角、构图、几何与真实可见细节。允许执行已声明的摄影外观变化。 |
| B：参考图 | 提供可观察、可比较、可迁移的摄影外观；需要分清调色/影调与材质、照明、姿态、视角差异。它不是像素级真值。 |
| C：输出图 | 保持 A 的场景与内容，达成冻结的参考外观目标；保留原生文件、交付变换与分项验收结果。 |

当前默认处理同场景、可能未对齐的两图与已声明的 SDR 显示域。跨场景风格泛化、多场景风格学习、RAW/HDR 成像训练和视频不自动并入本阶段。

## 3. “完整分析与迁移”应落实为什么

完整性首先指分析和目标覆盖完整：每项相关维度必须说明形成什么目标、已经满足什么、什么需要保持、什么不可比较或证据不足。它不要求每张图都执行所有类型的修改。

固定核查维度：中性色/白平衡、分色相的色相与彩度、肤色呈现、阴影/中间调/高光、高光过渡、局部对比、主体与背景关系、纹理与噪声观察。纹理观察服务于保真边界，不授权复制 B 的毛孔、发丝或织物细节。

用户要求的参考属性必须明确纳入目标及验收；需要降为可选、排除或不可判断的项目必须给出理由。当前案例的脸部提亮、自然暖肤和黄色柜板三项只是开发样例，不代表系统最终只需三项目标。通用提亮、暖化、增加饱和度不能单独证明参考外观得到充分利用。

单张已处理的 B 不能唯一确定原始相机 ISP、摄影师全部操作或未出现区域的风格变换。当前目标是推理阶段的参考属性分析与迁移；后续宣称可跨场景复用完整 look 时，需要匹配的数据与实验依据。

## 4. 参考图参与的完整工作流

| 阶段 | 对最初目标的具体责任 |
|---|---|
| 输入与预检 | 冻结 A/B 角色、来源、方向、编码和几何；判断参考是否适配，保存原文件。 |
| 系统诊断 | 同时分析 A 的状态、B 的外观、可迁移差异和 A 的保护事实；判断需要编辑、已经满足或证据不足。 |
| 按需证据 | 为对应语义区域使用独立 A/B 坐标，按属性判断可比性；测量、视觉观察、推断和不确定性分开记录。 |
| 目标与提示编译 | 把差异及证据转换成冻结的逐属性目标，区分参考事实、修改方向和成功条件；保存每项目标进入实际编辑条件的位置。 |
| 图像执行 | 将原始 A、B 和最终目标条件交给真实编辑后端；记录实际模型身份、预处理、全部输出、原生尺寸和调用次数。 |
| 独立验证 | 用 A 检查内容与保真，用 B 和冻结目标检查参考属性；逐项判断达成、残差、副作用及不确定性。 |
| 有限反馈 | 只对有证据且可修正的残差调整执行计划；目标与验收标准保持冻结，下一轮仍从原始 A+B 编辑。已经满足时保留原图。 |
| 可视化与报告 | 每步能看到参考观察、对应区域、差异、证据、目标、实际提示、候选、验收结果和失败原因。网页操作要能引导完成整个任务。 |

同一条任务应能追溯：参考观察/源图状态 → 差异及证据 → 目标 ID → 编辑条件 → 候选 → 对该目标的验证 → 反馈理由。只有提示写得详细，不能替代这条链的实际约束。

## 5. 已同意的实施顺序

1. 先用 GPT Image 2 作为单一编辑器范例，完善完整的参考分析、证据、提示、编辑、验证、反馈和逐步可视化。分析/验证由实际部署的 VLM 或 Agent 执行，不能混称为图像编辑器的文字诊断能力。
2. 用实验查明参考输入、显式诊断和结构化目标分别能否带来收益，以及有哪些失败边界；真实输出全部保留，证据不够就保留不确定性。
3. 将得到验证的改动整合回原始 HarnessIR 工程、命令入口和方案文档，保留历史合同与旧案例语义，并上传到用户指定 GitHub 仓库。
4. 单模型流程稳定后，将同一参考属性合同和验收语义适配到 Qwen、FireRed、FLUX、FIBO 的原生条件接口，分别验证模型特性带来的实际收益。

四模型适配是后续兼容目标。当前网页和实验脚本是开发与审查载体，最终改动需要进入原始工程并形成可运行、可恢复、可审计的路径。

原工程 v3 已有 A/B 参与的诊断、证据、共享意图、原生编译、编辑、共同验证和从原 A 反馈的骨架。后续应复用这个基础，重点贯通逐属性的源/参考观察、可比性、成功标准、目标覆盖，以及“已经满足”的成功终点；不能把现有工程误述为只有双图接口。

## 6. 什么才算任务完成

| 验收维度 | 完成要求 |
|---|---|
| 参考外观达成 | 所有请求的必需属性达到生成前冻结的标准；可选项及未达成项单列，不能用一个 accepted 隐去。 |
| 内容与自然度 | A 的身份、表情、对象、文字、构图与几何受保护；没有严重伪影、参考内容污染或无依据细节生成。无法确认时记录不确定。 |
| 交付条件 | 按事前声明检查画布、原生尺寸、允许变换和关键细节；插值后的尺寸不能证明恢复原始细节。 |
| 系统闭环 | 正确处理已经满足、参考不适配、证据不足、验收失败、预算耗尽和未知提交状态，结果与报告可追溯。 |
| 实验依据 | 区分软件规则通过、单例外观观察、真实模型效果与跨场景稳定性；只有证据覆盖的范围才能宣称完成。 |

属性更接近 B 与保护 A 同时成立，才符合业务目的。原图已经满足目标时，零次编辑返回原图同样是正确完成。

## 7. 现有实验对后续修改的约束

| 已观察到的问题或现象 | 对后续工程修改的要求 |
|---|---|
| 普通 A-only 修图也能通过本例的提亮/暖肤必需项 | 不以方向性改善代替参考利用证明；完善目标覆盖、参考干预与相同预算的基线比较。 |
| 带 B 图的条件在柜板上更接近 B，但完整流程未在所有属性上胜出 | 保留区域性的有限结论；查明诊断/条件表达是否遗漏，不预设流程越复杂效果越好。 |
| A+A 自参考仍出现显著提亮暖化 | 将无需修改的诊断和执行前停止路径纳入真实验收；当前控制器仅在收到正确导入合同后验证了零调用机制。 |
| 原生文件尺寸低于本轮冻结要求 | 将外观验收与交付验收分开；对不能满足的后端能力明确失败或交付限制。 |
| 部分 ROI 曾混入头发、镜框或不同光照 | 在生成前约束证据有效性和属性级可比性；保留原记录，新证据使用明确版本。 |
| 当前只做了单案例、少量重复和两个明显验证器控制 | 继续验证关键失败路径，之后才扩大跨场景与四模型结论；不把本轮通过率当一般可靠性。 |
| 宿主图像工具没有公开后端型号 | 当前结果保留 unknown/unverified；正式 GPT Image 2 与四模型结论需要身份可核对的执行。 |

这些是改动依据和待验证要求，不表示本文已经实现对应工程补丁。完整已执行范围见 [V2 实验结果](CASE_EXPERIMENT.md)，本次工程整合见 [运行手册](RUNBOOK.md)。
